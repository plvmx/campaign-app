# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Git workflow

### Autonomous (no approval needed)
- Create feature branches (`git checkout -b <branch>`)
- Stage and commit changes — always with a clear message summarising *why*
- Push feature branches to origin (`git push origin <feature-branch>`)
- Create PRs (`gh pr create`) — include summary, test plan, and link to any related task
- Check CI status (`gh run list`, `gh run view`)
- Fix CI failures and push follow-up commits to the same branch

### Always pause and wait for explicit "go ahead"
- **Merging a PR to main** (`gh pr merge`) — main auto-deploys to production
- **Pushing directly to main** — blocked in settings; if ever needed, ask first
- **Force-pushing anything** — blocked in settings; never bypass without discussion

### Communication
- After every commit, state: branch name, commit hash (short), and one-line summary
- After every push, confirm where it went and whether CI was triggered
- When creating a PR, share the URL so Peter can review before approving the merge
- If CI fails, diagnose and fix without asking — then report what was wrong and what changed

## Branch naming
`<type>/<short-description>` — e.g. `fix/campaign-date-filter`, `feat/pagination`, `chore/update-actions`

## Code quality (standing rule)
Every change must pass all four CI jobs: **Lint · Type-check · Unit tests · Build**.  
Never suppress lint errors with disable comments unless there is no correct refactor — always prefer fixing the root cause.

## Testing policy
- Every bug-fix PR includes a regression test that fails on the pre-fix code and passes on the post-fix code, in the same PR. If the bug is purely visual/CSS/copy and genuinely can't be captured in a test, say so explicitly in the PR description rather than silently skipping it.
- Every new function added to `lib/` or `lib/services/` ships with a test in the same PR.
- Before calling a fix "done," verify red→green: run the new/updated test against the pre-fix code (e.g. `git stash`, or check out the parent commit for a specific file) to confirm it actually fails, then against the fix to confirm it passes. A test that currently passes is not sufficient on its own — it must be shown to have caught the original bug.
- Mock the Supabase client with the shared builder in `lib/services/__tests__/supabaseMock.ts` rather than hand-rolling `vi.mock` chains per test file.
- If a production incident is investigated with a one-off script in `scripts/`, the investigation isn't closed until the root cause is captured as a permanent test in `lib/__tests__/` (or `lib/services/__tests__/`) — the script is evidence, not the fix's safety net.
- Role/status checks against `state_leaders.admin` must go through `isRecognizedAdminStatus()` in `lib/campaignFilter.ts` — never re-implement `=== 'AD' || === 'SR'` inline. See #78 (login role bug) for why: a truthy check in one call site silently misrouted leaders with junk data in that column.

## Pre-PR checklist (standing rule)
Before opening a PR, work through this list and note the outcome of each item in the PR description (a plain "N/A" is fine — don't skip silently). This exists because it's easy for backups, docs, and cleanup to quietly fall behind as the app grows.

1. **Backups in sync** — did this change add, remove, or rename a database table, or change a column that a backup depends on? If so, update `BACKUP_TABLE_CONFIG` in `lib/services/backupService.ts` (new tables go in FK-safe order — only after every table they reference), bump the export format `version` per the comment above it, and confirm `/admin/backup` still exports/restores cleanly.
2. **Docs in sync** — `TECHNICAL_DOCS.md` must be updated in **every** PR that changes code it describes (Peter's explicit standing request; it had silently fallen ~40 commits behind by 2026-10-16). Check its §4 folder structure, §5 schema, §6–7 auth/roles, §8 routes, §10 services, §14 env vars (the §22 list). Also update `CLAUDE.md` itself in the same PR if the change touches its Architecture section, and `README.md` if it changes setup steps, env vars, or user-facing behaviour. The PR description must say what was updated in `TECHNICAL_DOCS.md`, or "N/A" with a reason — never omit the line.
3. **Quality pass** — run `/code-review` (or `/simplify`) against the diff, specifically looking for redundancy the change introduced: logic that duplicates an existing `lib/services/` function, inline role checks bypassing `isRecognizedAdminStatus()`, repeated/N+1 Supabase calls that could be batched, or dead code left behind by the change. Either fix what's found in this PR, or note it explicitly as a follow-up in the PR description — don't let it pass unmentioned.

## Architecture

### Stack
- **Next.js 16 App Router** — all pages live under `app/`. No Pages Router.
- **React 19** with client components (`'use client'`) for all interactive UI.
- **Supabase** (`@supabase/supabase-js`) — Postgres database + auth. Two clients:
  - `lib/supabaseClient.ts` — browser client, used everywhere in the frontend.
  - `lib/supabaseAdmin.ts` — service-role client, used only in API routes.
- **Tailwind CSS v4** — utility-first styling, dark-mode via `dark:` variants.
- **Vitest + jsdom + React Testing Library** — unit tests in `lib/__tests__/`.

### Auth & roles
- Login is mobile-number + name via `lib/auth.ts` (`signInWithMobileAndName`).
- Role is resolved at runtime from the `state_leaders` table:
  - `admin = 'AD'` → full admin
  - `admin = 'SR'` → state reporter (can only see/edit their own state)
  - Otherwise → regular user
- `contexts/UserContext.tsx` (`useUser()`) is the single source of truth for the current user, profile, role (`isAdmin`, `adminStatus`), state, and leader. Pages read from this context rather than querying auth themselves.
- Role checking is done inline: compare `adminStatus === 'AD'` (full admin) or `adminStatus === 'SR'` (state reporter). No permissions module — role logic lives in `UserContext` and `campaignFilter.ts`.
- **Leader email capture (Phases 1-3 of a longer rollout toward real Supabase Auth + MFA for every leader)** — `state_leaders` now carries `email`/`pending_email`/`user_id`/`email_confirmed_at` (`scripts/add_email_to_state_leaders.sql`), but login itself is unchanged so far: mobile+name is still the only active identity check, and `user_id` isn't read by any RLS policy yet. Right after a successful mobile+name sign-in, `/login` shows a skippable step asking a leader with no confirmed `email` to add/confirm one — pre-filled from `pending_email` or a `registry.registrants` phone-match suggestion (`lib/services/registrantEmailSuggestionService.ts`; a suggestion only, never written back to `state_leaders` directly, since that table has no reliable identity key to a specific leader — see `lib/registryPipeline/leaderMatch.ts`'s own comment on why it matches by phone instead). Submitting calls `POST /api/auth/propose-email`, which re-verifies the same mobile+name pair server-side (`lib/services/leaderVerificationService.ts`'s `findVerifiedStateLeaders` — a bare leader id is never trusted) before writing `pending_email` and sending a real Supabase magic link. The magic-link redirect also carries the leader id as a `?leaderId=` query param (set by `propose-email`), which the `/confirm-email` page (`lib/emailConfirmSupabaseClient.ts` — an isolated Supabase client with its own localStorage key, exactly mirroring `lib/registrySupabaseClient.ts`, so detecting/signing-out of this magic-link session can't collide with the leader's real anonymous app session) forwards to `POST /api/auth/confirm-email` alongside the session's access token; that route trusts only `supabaseAdmin.auth.getUser(token)` for the confirmed email (never a client-supplied string) but scopes its commit to that one `leaderId` + matching `pending_email` — never a blanket match on the email string alone, since two different leaders could otherwise propose the same address (a shared household email, or a typo) and whichever confirms first would silently attach their identity to the other's row too. A leader with several `state_leaders` rows — whether across states, or multiple rows within one state (an AD row, an SR row, and/or a plain leader row, differentiated by name/mobile to satisfy the table's own state+leader uniqueness) — confirms each row independently this way and they can all share one address; `email` has no DB-level uniqueness constraint (dropped in `scripts/drop_state_leaders_email_unique_index.sql` after that turned out to block exactly this, a live rollout blocker — see the removal script's own comment for why the app-level leaderId-scoping above is protection enough on its own). Every confirmation is logged to `state_leader_email_changes`. Admins can also set a leader's `email` directly from `/admin/state-leaders` with no click-verification required (a stronger trust bar than the self-serve path). Notifying a leader's *old* email address on change is deliberately deferred — this app has no outbound transactional email capability outside Supabase Auth's own magic-link template, and it isn't needed yet since `email`/`user_id` aren't privileged credentials until a later phase rewrites RLS to key off `user_id`.
- **MFA enrollment (unenforced)** — the next step after email capture, before the actual login-flow switch and RLS rewrite. `state_leaders.mfa_enrolled_at` (`scripts/add_mfa_enrolled_at_to_state_leaders.sql`) records when a leader who already has a confirmed `email` sets up an authenticator app (TOTP) as a second factor — nothing about login/RLS changes yet, and it's fully skippable, same as the email step. Shown right after the email step exits (`/login`'s `maybeShowMfaStep`), only once `email` is set and `mfaEnrolledAt` isn't. "Set up now" calls `POST /api/auth/request-mfa-setup` (`{leaderId, mobile, firstName}` — leaderId scoped like `propose-email`'s own, since a multi-row person's rows can carry *different* confirmed emails if they signed in/confirmed under different mobile+name pairs, and sending the link to the wrong one would strand them without that inbox) which re-verifies mobile+name, confirms that specific row has a confirmed email, and sends a plain Supabase magic link to `/setup-mfa`. That page reuses `lib/emailConfirmSupabaseClient.ts` (now shared with `/confirm-email` — same "isolated session to prove identity" shape, though unlike `/confirm-email` this session has to stay alive through a multi-step enrollment UI rather than signing out immediately; a bounded 5-minute abandonment timeout signs it out and expires the link if enrollment is left mid-flow, since `state_leaders`' RLS grants any authenticated session read access to every leader's row), then goes straight into TOTP enrollment — no method-choice screen, since an authenticator app is the only option Peter decided to offer (2026-09-27; SMS was built, then deliberately removed before ever being enabled — see below). TOTP mirrors `/registry/mfa/enroll`'s exact mechanics (stale-unverified-factor cleanup scoped by `factor_type` before a fresh `enroll()`, QR rendered client-side from `data.totp.uri` rather than Supabase's own bloated `qr_code` SVG) — `enroll()` passes an explicit `friendlyName` ("AFJ Campaign App (Authenticator)"), since this app and `/registry` share the same underlying Supabase Auth user pool and both otherwise default to the same blank name, which collides for a leader who already has a verified `/registry` TOTP factor under the same email (confirmed live, 2026-09-26). Fixing the name collision surfaced a second, deeper issue from the same shared-user-pool fact: once an account has *any* verified factor at all (from `/registry` or a prior enrollment here), Supabase requires the session to already be at AAL2 before it will allow enrolling another one, regardless of `friendlyName` (`"AAL2 required to enroll a new factor"`, confirmed live the same day). `/setup-mfa`'s sign-in handler now checks `getAuthenticatorAssuranceLevel()` right after sign-in — `nextLevel === 'aal2' && currentLevel !== 'aal2'` means "has a verified factor, hasn't proven it this session" — and if so shows a `step-up` screen that challenges the existing verified factor (`challengeAndVerify`); cancelling (or backing out of TOTP enrollment itself, same `handleCancel`) signs out and shows a "no problem, another time" screen rather than a dead end. A successful step-up goes straight to `finishEnrollment()` rather than on to a fresh TOTP enroll — the existing verified factor (whichever app enrolled it) already satisfies MFA for this account, so asking the leader to also scan a brand-new, app-specific QR code would just be a confusing duplicate (Peter reported exactly this live, 2026-09-26, same day as the AAL2 fix that introduced it). On success, `POST /api/auth/complete-mfa-setup` (Bearer token only, and — since a valid token alone isn't proof `challengeAndVerify()` actually succeeded — only if `supabaseAdmin.auth.getUser(token)`'s own `user.factors` shows a verified one) sets `mfa_enrolled_at = now()` on every `state_leaders` row already sharing that `user_id` — the same per-row confirmation granularity `email` already has, not automatically propagated to a person's other unconfirmed rows.
- **SMS/phone MFA — built, then removed before ever being enabled, 2026-09-27** — the original build offered a `choose-method` screen (authenticator app vs. text message), with a `factorType: 'phone'` branch gated behind `NEXT_PUBLIC_SMS_MFA_ENABLED` (unset by default, since connecting a real SMS provider — Twilio, MessageBird, Vonage — in the Supabase dashboard was never done). Peter decided to start with authenticator-app-only MFA rather than give leaders a choice, so the phone branch, the choice screen, and the env var were deleted outright rather than left dormant behind the flag — there was no reason to carry the extra screens/state/tests for an option nobody could ever reach. `lib/clickSendClient.ts`'s unrelated app-level "text the leader" SMS integration is untouched by this. Missed on the first pass and fixed the same day once Peter spotted it live: `/login`'s own MFA-offer step (`mfaStep`, separate from `/setup-mfa`) still had copy mentioning "an authenticator app or a text message code" and "choose and set up your authentication method" — updated to say authenticator app only.
- **Real-auth + MFA login (hybrid cutover, 2026-09-28)** — since not every leader will confirm email + enroll MFA before MFA needs to be load-bearing, this is a *hybrid*, not a hard cutover: a leader with a confirmed `email` and `mfa_enrolled_at` set gets a brand-new login path (`/login/mfa` → `/login/mfa/callback`) that replaces mobile+name entirely — email + magic link + TOTP code instead. Everyone else keeps today's mobile+name flow completely unchanged (`/login` just gained one link to `/login/mfa` — removed 2026-10-15 as redundant: an enrolled admin who types mobile+name is sent to email sign-in by `getAdminLoginGate`, and a plain leader is routed there via `?require2fa=1` when they open members' details). Mirrors the `/registry` portal's already-shipped real-auth+MFA mechanics (magic link → callback → AAL2 gate/challenge → persistent session, never signed back out) applied to `state_leaders.user_id` instead of `registry.leader_roles`, using the **main** `lib/supabaseClient.ts` client rather than an isolated one — unlike `/confirm-email`/`/setup-mfa`, this magic-link session is *meant* to become the leader's new persistent identity, replacing whatever anonymous session existed (that client already has `detectSessionInUrl: true`, so the callback picks up the session automatically). No RLS changes were needed for this: today's mobile+name login (`completeSignIn()`) already resolves "who is this / are they admin" purely from `user_profiles`/`user_roles` rows keyed to `auth.uid()` — regardless of whether that `auth.uid()` came from an anonymous sign-in or a real one — so the new flow just needed to write those same rows against the real, persistent identity instead (new `completeLeaderAuthSignIn()` in `lib/auth.ts`, sharing a `setAppSessionCookie()` helper with `completeSignIn()`). One behavior `completeSignIn()` never needed: since the real `user_id` persists across logins (unlike a fresh anonymous user every time), picking a *different* role on a later login must not leave a stale `user_roles.role = 'admin'` row from a previous choice — a non-admin pick explicitly `DELETE`s any existing row rather than just never upserting one. `/login/mfa/callback` resolves every `state_leaders` row sharing the signed-in `user_id`; exactly one signs straight in, more than one shows a role picker labeled by role via `lib/leaderRoleLabel.ts`'s `getLeaderRoleLabel()` (`AD` → "Admin", app-wide so no state suffix; `SR` → "State Reporter — VIC"; plain → "Leader — VIC", changed from a bare state code the same day per Peter's request — it read as unlabeled next to "Admin"/"State Reporter") — a real improvement over the mobile+name flow's multi-state picker, which can't distinguish AD/SR/plain rows in the same state at all and instead forces a leader to use different mobile/name credentials per role. The `app_session` cookie this flow sets gets a 30-day expiry (Peter's call) rather than the mobile+name flow's plain session-cookie behavior, since email+MFA has more per-login friction than one instant form and the underlying Supabase refresh token already supports staying signed in that long. The shared `CodeEntryScreen` component (`components/auth/CodeEntryScreen.tsx`, extracted from `/setup-mfa` the same day so both flows' code-entry screens stay identical without duplicating it) is reused by the callback's TOTP-challenge step. Deliberately **not** changed by this pass: RLS (`public.is_admin()` and every leader-ownership policy in `supabase/rls-policies.sql`), `lib/campaignFilter.ts`, `lib/services/authService.ts`, `contexts/UserContext.tsx`, the four duplicated admin-check API routes, `app/api/admin/invalidate-user-session`, and `middleware.ts` (unaffected — `/login/mfa*` already falls outside every protected prefix) — a later, separate phase can rewrite RLS to key directly off `state_leaders.user_id` once the anonymous path is fully retired.
- **Follow-up: switch role without signing out, and skip straight to email sign-in on a returning device, 2026-09-28** — Peter reported two rough edges live the same day this shipped. First, a leader with more than one `state_leaders` row had no way to pick a *different* one without fully signing out and back in — since the real session is already at AAL2, `components/MobileLayout.tsx` now shows a **Switch Role** button (next to Sign Out, only when `supabase.auth.getSession()`'s `session.user.is_anonymous === false`) that just navigates to `/login/mfa/callback` again; that page's existing `getSession()` race-cover branch already re-resolves the leader's rows and re-shows the role picker with no new magic link or TOTP challenge needed, since AAL2 already holds for that session. Second, Peter asked why signing out required a brand-new magic link rather than just a fresh TOTP code — that part is correct as designed (there's no password; email verification *is* the primary credential, and a full sign-out revokes the session entirely), but it highlighted that a returning, not-currently-signed-in leader still had to click through the mobile+name form and then "Sign in with email instead" every time. `lib/emailLoginPreference.ts`'s `PREFERS_EMAIL_MFA_LOGIN_KEY` is now set in `localStorage` (never cleared on sign-out, same precedent as `/login`'s own remembered mobile/name fields) right after a successful `/login/mfa/callback` sign-in; `/login`'s session check reads it and, when no active session exists, redirects straight to `/login/mfa` instead of showing the mobile+name form first. `/login/mfa`'s "back to mobile+name" link passes `?mode=mobile`, which `/login` checks to bypass that redirect just once without touching the remembered preference — without it, that link would otherwise bounce straight back to `/login/mfa` in a loop (caught in manual testing before shipping).
- **Follow-up: the "prefers email sign-in" marker is now admin-only by default, 2026-10-13** — testing the new 2FA flow, Peter found that PVTester (plain leader) was bounced to the email sign-in screen on every sign-out: the marker above was set for *any* email + 2FA sign-in and redirected every signed-out `/login` visit. It now has two strengths (`rememberEmailLogin(admin)` / `shouldSkipToEmailLogin({ requireTwoFactor })`, `lib/emailLoginPreference.ts`): `'always'` for an admin (AD/SR — they can't use mobile+name), `'when-required'` for anyone else, who keeps seeing the mobile+name form by default and is only skipped to email sign-in when they arrive from `/login?require2fa=1`. Never downgrades an `'always'` device; the old marker value `'1'` reads as `'when-required'`, so existing plain-leader devices stop bouncing immediately and an admin's next email sign-in upgrades theirs. **Shared-device caveat (2026-10-14):** the marker is per *browser*, not per person, so a browser that has ever been used for an admin email sign-in stays `'always'` for everyone who uses it (Peter's own test laptop, signing in as admin and as PVTester). The way out is always `/login?mode=mobile` (bypasses the redirect once); the "Not set up yet" screen on `/login/mfa/callback` — shown, e.g., to a leader whose 2FA was just reset — used to link to bare `/login` and so looped back to email sign-in on such a device; it now links to `/login?mode=mobile`.
- **Typed-code fallback for all three magic-link flows — Apple Mail Privacy Protection, 2026-10-05** — a cluster of leaders (38 of 173, more than the 21 who'd successfully confirmed) were found to be authenticating successfully at the Supabase level on every attempt (`auth.users.last_sign_in_at` updates every time, including repeated retries across many days) while the app-side confirmation step never ran — zero matching requests ever reached `/api/auth/confirm-email`, confirmed via Vercel logs on a fresh, real-time attempt. Traced to Apple Mail Privacy Protection (on by default since 2021): Apple's servers pre-fetch linked content before a user opens an email, and Supabase's magic-link verify endpoint treats any GET as a valid one-time redemption with no way to tell a prefetch from a real click — so the token is silently consumed before the leader ever taps it, and they land on an "expired link" screen that (via its own "back to sign in" link plus an already-valid app session) reads as "it just goes back into the app." Confirmed live for the leader traced deepest: Apple Mail on a Mac. This affects `/confirm-email`, `/setup-mfa`, and `/login/mfa` identically, since all three rely purely on a clickable link. Fix: a collapsed-by-default "If the link is not working, click here to enter the code from the email instead" option (`components/auth/InlineCodeFallback.tsx`, reusing `components/auth/CodeEntryScreen.tsx`'s style constants) added to all three "check your inbox" screens (`/login`'s `emailStep`/`mfaStep` phase `'sent'`, and `/login/mfa`'s `sent` state) — a typed code can't be silently consumed by a prefetcher the way a link can. Each site calls `verifyOtp({ email, token: code, type: 'email' })` on whichever Supabase client the corresponding landing page already expects (the isolated `emailConfirmSupabase` for the email-capture and MFA-setup steps, the main `supabase` client for the real-auth login step), then either calls the existing `/api/auth/confirm-email` route directly (email capture — reusing it unchanged, same request shape `/confirm-email/page.tsx` itself makes) or just `router.push()`s to the existing landing page (`/setup-mfa`, `/login/mfa/callback`) — both of which already have a `getSession()` race-cover built for "a session already exists by the time this page's listener subscribes," so they pick up a code-established session with zero code changes of their own. **Requires a one-time Supabase Dashboard change** (not scriptable): the "Magic Link" email template needs `{{ .Token }}` added to its body — Supabase already generates this code for every `signInWithOtp()` call, it just isn't shown in the email by default. One template covers all three flows.
- **Follow-up: the code fallback also needed to live on the failure screen, not just the sending screen, 2026-10-05** — Peter asked how a leader would even know to use the code, which surfaced a real gap in the fix above: a leader's actual journey is submit email → see "check your inbox" → move on (the code option above lives right there, but they've typically left that screen by the time anything goes wrong) → later, open the email and tap the dead link → land on an "expired/invalid" screen whose only option was "Back to sign in" → bounce straight back into the app if already signed in via mobile+name, with no visible sign anything failed (this is exactly what Alan described). The code option on the *sending* screen never helps here, since the leader is no longer on it. New `components/auth/EmailAndCodeFallback.tsx` — shown directly (not collapsed, unlike `InlineCodeFallback`, since this already *is* the recovery screen) on the "expired/invalid link" screens of all three landing pages (`/confirm-email`, `/setup-mfa`, `/login/mfa/callback`). Unlike the sending-screen version, these pages never collected an email (they only ever had the link to go on), so this form asks for both email and code. Mechanically simpler than it sounds: each page's `onAuthStateChange` listener (registered on mount) stays subscribed for the component's lifetime regardless of which screen is showing, and the failed first attempt never actually ran `handleSignedIn` (so `handledRef` is still `false`) — so the recovery handler only needs to call `verifyOtp()` and throw on failure; a success fires the exact same `SIGNED_IN` event the original link would have, and the page's own already-existing logic runs unmodified. Zero other code changes to any of the three pages beyond rendering the form and that one small handler each.
- **Follow-up: the "check your inbox" screen's own button was leading leaders to skip the real link, 2026-10-05** — Alan (the leader this whole fallback effort traces back to) reported a third incident after the above two shipped: having confirmed his email, he clicked "Set up now" for MFA, but was "taken straight into the app" without ever seeing the QR code screen. A fresh DB check (`auth.users.recovery_sent_at` updated, but `last_sign_in_at` never updated again afterward) proved he never actually verified the MFA magic link at all — Apple Mail Privacy Protection was ruled out this time; he simply never clicked it. Root cause: `app/login/page.tsx`'s `emailStep`/`mfaStep` "check your inbox" screens (phase `'sent'`) had a big, prominent, primary-styled **"Continue"** button that calls the exact same `handleEmailStepDone`/`handleMfaStepDone` dismiss-and-proceed handler as the plain-text "Skip for now" link one screen earlier for the identical action — just relabeled, and styled as if it were the main next step. A leader skimming the screen reasonably reads a big blue "Continue" button as "click here to proceed" and never opens their inbox at all. Fixed by renaming both buttons to **"Skip for now"** and restyling them to match the existing subdued, secondary-link style already used for that exact action elsewhere in the same flow (`text-sm text-blue-600`, not `bg-blue-600`/`font-bold`) — so the only prominent action left on these screens is the typed-code fallback added above, not a fake "proceed" button. No behavior change (same handlers, same destinations) — copy and visual-prominence only.
- **Follow-up: pasted codes were being silently truncated, and the code-fallback link now reads as a link, 2026-10-06** — Alan, after finally getting through, reported pasting the emailed code didn't work. All three code inputs (`InlineCodeFallback`, `EmailAndCodeFallback`, `CodeEntryScreen`) used `maxLength={6}`, which truncates a paste to its first 6 characters *before* any cleaning — a copied code with a leading space/newline/label (very common when selecting text from an email) became a wrong 6-character string. Now `lib/otpInput.ts`'s `normalizeOtpInput()` strips non-digits and caps at 6 on every change (no `maxLength`). The sending-screen toggle's "Click Here" is also underlined/bold so it reads as a link. Code expiry itself is a Supabase Dashboard setting (Authentication → Providers → Email → Email OTP Expiration, default 1 hour), not app code.
- **Follow-up: clearer "check your inbox" wording, 2026-10-09** — many leaders aren't computer-literate, so the three post-send messages (`/login`'s `emailStep` and `mfaStep`, and `/login/mfa`) now all say "We have sent an email … Open that email and click the **CONFIRM NOW** link in it …" plus a Junk/Spam hint. The label deliberately matches the link text in Supabase's single "Magic Link" template (shared by all three flows, so the label has to be generic) — if that template's link text changes, update these three messages to match.
- **Follow-up: emailed codes aren't always 6 digits, 2026-10-09** — a leader's email showed an 8-digit code while the typed-code box only accepted 6 (every code input was hardcoded to 6, including the cap added in the paste fix above). Now: (1) the database enforces it — `scripts/require_mfa_for_member_details.sql` (mirrored in `supabase/rls-policies.sql`) adds `(auth.jwt() ->> 'aal') = 'aal2'` to the SELECT/UPDATE policies on `campaign_interest` and `training_interest`, so a mobile+name (anonymous, aal1) session simply cannot read those rows; (2) the screens that show them (`/campaign-interest`, `/training-interest/[campaignId]`) are wrapped in `components/auth/RequireTwoFactorForMemberDetails.tsx`, which checks the session's AAL and otherwise explains why and calls `lib/twoFactorSetup.ts`'s `startTwoFactorSignIn()` (sign out → `/login?require2fa=1`); (3) `/login?require2fa=1` gates a *plain* leader exactly like an admin (`getAdminLoginGate(match, { requireTwoFactor })` — no app session is created via mobile+name, the email + 2FA steps have no skip, an enrolled leader is pointed at `/login/mfa`); at a normal sign-in plain leaders get no email/2FA prompt at all, and My Admin (`/app/tl-admin`) has an optional "Extra Security" card using the same entry point. Leaders still see *how many* people registered (the "N people interested" note, the "Manage my Campaign/Training Interest" buttons) — those counts come from `POST /api/leader/interest-counts` (`lib/services/interestCountsService.ts` — numbers only, service role, but restricted to campaigns the caller's own JWT can see via `campaigns` RLS), since the rows themselves are now hidden from an aal1 session. Members/registrants are never Supabase users; only the *viewing leader's* session level matters. Admins (AD/SR) are unchanged — mandatory 2FA already. **Deploy order:** ship this code first, then run the SQL (running it first makes the counts read zero for everyone not at aal2). Rollback: re-run the policy blocks from the pre-change `rls-policies.sql`.

- **Follow-up: `/login` no longer loops on a session the server has rejected, 2026-10-14** — Peter's phone hung on "Checking sign-in status…" signing in as Peter_AD. `/login`'s on-load check used `getSession()`, which only reads the copy saved on the device, so a session Supabase had since rejected (most likely an old anonymous Peter_AD session banned by `scripts/revoke_admin_app_sessions.ts`) still looked signed in: `/login` sent it to `/app`, `/app`'s own server check (`UserContext` → `getUser()`) sent it back to `/login`, forever. `/login` now uses `lib/auth.ts`'s `getVerifiedSession()`, which also asks the server (`getUser()`); a rejected session is cleared from the device (local sign-out + `app_session` cookie) and the sign-in form shows; a network failure shows the form without clearing anything.

- **Follow-up: `/login/mfa/callback` could freeze on "Signing you in…", 2026-10-14** — right after the fix above, Peter_AD's phone verified the email link (auth `last_sign_in_at` updated) but never reached the authenticator-code step. On a scanner-proof link the page's `getSession()` race-cover still ran on load, so an older session already saved on the device claimed `handledRef` before the tap; the tapped sign-in's `SIGNED_IN` was then ignored, and the post-tap give-up timer (which only checks `handledRef`) never fired. Now a session can't claim the sign-in while a token is waiting for the tap (`awaitingTapRef`); once a sign-in is under way, "Signing you in…" turns into a "taking too long — Start again" screen after 20 s (`STUCK_AFTER_MS`), as does any exception in the role/MFA lookups; and a refused grant on the no-challenge path now shows its error instead of an unchanged "Signing you in…".
- **Follow-up: the same safeguard on `/confirm-email` and `/setup-mfa`, 2026-10-14** — both had the identical wait-for-`SIGNED_IN` pattern, so they get the same `awaitingTapRef` guard and the same 20-second "This is taking too long — Start again" screen. The time limit and that screen are shared by all three pages via `components/auth/SigningInStuck.tsx` (`useStuckWatchdog`, `SigningInStuck`, `STUCK_AFTER_MS`).

- **Browser Supabase clients no longer wait forever for a stuck tab, 2026-10-14** — Peter_AD, signed in as admin on his phone, sat on "Loading…" for minutes. supabase-js's default auth lock is a Navigator lock shared by every tab of the app on the device, requested with **no time limit**; each email link can open a new tab, and a tab the phone froze in the background while holding that lock blocks every other tab's `getSession()`/`getUser()`/queries indefinitely (reproduced locally: a second tab holding the lock left `/login` on "Checking sign-in status…" for good — plausibly also behind the earlier "Signing you in…" freeze). All three browser clients (`lib/supabaseClient.ts`, `lib/emailConfirmSupabaseClient.ts`, `lib/registrySupabaseClient.ts`) now pass `lock: createNonBlockingAuthLock()` (`lib/supabaseLock.ts`): same cross-tab lock, but an unlimited wait becomes `AUTH_LOCK_WAIT_MS` (5 s) and is then taken over (`steal`) instead of hanging; "only if free" calls (timeout 0, the background refresh ticker) are unchanged, and an error from the locked work itself never re-runs it.

Built from a **build-time manifest** (`scripts/build-tech-insights.ts` → gitignored `generated/tech-insights/`, run by `predev`/`prebuild`; pure logic in `lib/techInsights/buildManifest.ts`) rather than runtime React introspection, because React 19 removed `_debugSource` and production builds minify names. Served only via `GET /api/admin/tech-insights` (`verifyAdminCaller`, AD + aal2; source only for paths the manifest lists) — never in `public/` or the client bundle; `outputFileTracingIncludes` in `next.config.ts` ships the generated files with that function. `TechInsightsLoader` (mounted in `app/providers.tsx`) does nothing — no request, no listener — for non-admins and phone/touch devices; the panel and manifest load lazily on first keypress. **Phase 2 (visible components):** components carry `data-ti="<own file path>"` on their root element (attribute only; `TechInsightsMapTag` for Leaflet's `MapContainer`); the panel scans the DOM for them (`lib/techInsights/domScan.ts`) to add a "Visible on this screen" drop-down group, click-to-pick, on-page outlines and a tagged-ancestor chain. `tagsMatchSourceFiles.test.ts` keeps every tag pointing at its own file — **tag a new component by adding the attribute to its root element**. Static analysis finds only literal table/API strings. See `TECHNICAL_DOCS.md` §20.
- `components/MobileLayout.tsx` — shared shell (header, bottom nav) wrapping every page. Resolves admin status via `getUserAdminStatusAndMobile()`.
- `components/CampaignForm.tsx` — reusable add/edit form used by the admin panel; `CampaignData` interface includes a `category` field (e.g. `TWOL`, `BOTJ`, `TLT`).
- `components/ErrorBoundary.tsx` — global React error boundary.
- `app/app/components/AdminQuickActions.tsx` — the purple "Admin Quick Actions" box at the top of `/app`, shown to full admins (AD) only. Since 2026-10-12 it holds a **Check if a Person is Registered** button (→ `/admin/check-registration`), plus (2026-10-16) **Week 1 Campaigns** and **Campaign Results** buttons that open those public links (`/public/week1-campaigns`, `/public/campaign-results` — titles/paths read from `lib/publicLinks.ts`; opened via `components/BackToAppBar.tsx`'s `withBackToApp()`, which adds `?from=app` so `app/public/layout.tsx` shows a "← Back to app" bar — public pages have no app header, and members opening a shared link never see it); its four download buttons (Campaign Lists, Leader Campaign Lists, Campaign Results, Week 1 Campaigns) and All States drop-down were retired — the same outputs remain on `/admin/generate-slides`, `/admin/generate-report` and `/admin/generate-week-campaigns`.
- `components/AllLeadersCampaignListScreen.tsx` — full-screen "Upcoming Campaigns for All Leaders" (same data/list as `/public/temporary-upcoming-campaigns`, via `/api/public/temporary-upcoming-campaigns`; only a "Download a Copy" button and a return link). Opened in place from the green **Extras** link beside **More Info** on `/app`, shown to plain leaders only (not AD/SR). The Extras box also has a yellow **All Campaign Results for Last Week** button, which opens `app/public/campaign-results/CampaignResultsClient.tsx` in place via its `onClose` prop (full-screen overlay, no Save-to-Photos buttons, "Download a Copy of Page N" labels, return link; the IMPORTANT NOTICE is kept).
- `components/auth/MfaEnrollmentFlow.tsx` — the authenticator-app (TOTP) enrollment steps (AAL2 step-up if the account already has a verified factor, stale-factor cleanup, QR + code verify, `POST /api/auth/complete-mfa-setup`, abandonment timer) for an already-signed-in `emailConfirmSupabase` session; shared by `/setup-mfa` and `/confirm-email`. Always signs that session out before reporting its outcome (`success`/`cancelled`/`expired`) to the caller.
- `components/PdfGuideViewer.tsx` — draws every page of a PDF at screen width with pdf.js (`pdfjs-dist`, pinned to 5.4.x because 6.x needs Node 22 and CI runs 20; the **legacy** build, for older phones; loaded only when the guide opens). Used by `/app/guide` instead of the browser's PDF viewer, which can't be embedded reliably on phones (Android Chrome not at all) and has no way back into the app. Canvas sharpness capped at 2× (`lib/pdfRenderScale.ts`) to limit phone memory. Note when testing: pdf.js pauses drawing while the tab is hidden (e.g. a background preview tab), so pages after the first only appear once it's visible.
- `components/CampaignMap.tsx` — shared Leaflet map for "every upcoming campaign, no radius", used by the public `/public/upcoming-campaigns` (previously the admin-only "View Campaign Map") and the admin `/admin/state-places-map`. Its marker/campaign types are minimal local interfaces (`CampaignMapPopupMarker`/`CampaignMapPopupCampaign` — id/date/time/leader, mirroring `NearbyCampaignsMap.tsx`'s own pattern below) rather than the admin-only `Campaign` type, so a public caller's leaner rows satisfy it without a cast. A `renderActions` prop (defaulting to the admin `MapPopupActions` stub) lets each screen swap in its own popup actions — `/public/upcoming-campaigns` passes `components/PublicMapRegisterInterestActions.tsx` instead, which — since a general public visitor has no known identity to look up (unlike `/public/campaigns-near-me` below) — captures first name + mobile/email in its own confirmation modal before POSTing to `/api/public/register-interest`.
- `components/NearbyCampaignsMap.tsx` — shared Leaflet map for "campaigns within a radius of a point", used by both `/admin/campaigns-near-me` and the public `/public/campaigns-near-me`. A `renderActions` prop (defaulting to the admin `MapPopupActions` stub) lets each screen swap in its own popup actions — the public screen passes `components/PublicCampaignInterestActions.tsx` instead, which shows the same consent-confirmation modal as Register Interest ("Proceed"/"Cancel") before actually recording interest into `campaign_interest`. That confirmation reuses `components/Modal.tsx`, which now portals to `document.body` rather than rendering in place — needed once a modal could be triggered from inside a Leaflet popup, since Leaflet's panes carry a CSS `transform` that would otherwise make a `position: fixed` modal position itself relative to the map instead of the screen. Its campaign markers are rendered noticeably larger/darker (30px, 0.5 fill-opacity) than `CampaignMap.tsx`'s own default (22px, 0.35) via `lib/leafletMarkerIcon.ts`'s `getStateMarkerIcon()` `{ size, fillOpacity }` options (2026-09-17, Peter's request — this map is meant to be tapped on a phone) — `getStateMarkerIcon`'s icon cache is keyed on those options too, not just state+place, so two callers requesting different sizes for the same place never collide.
- `components/registerInterest/` — `RegisterInterestClient.tsx` (+ `CampaignCheckboxList.tsx`, `InterestSummaryModal.tsx`), the Register Interest screen shared by `/public/register-interest` (current fortnight) and `/admin/register-interest` (admin-only, `nextPeriod` prop — the fortnight after). Moved out of `app/public/register-interest/` once a second route needed it.
- `components/CampaignInterestEntryList.tsx` — the registration-row list (campaign info, interest-type badge, Contacted checkbox) shared by `/admin/registered-interest` (admin-wide) and `/campaign-interest` (leader-scoped).
- `contexts/CampaignDatesContext.tsx` — shared date-range state for campaign views.
- `app/app/components/useCampaignForm.ts` — unified form hook shared by `CampaignCreateForm` and `InlineEditForm`. Owns all form state (date, state, place, time, leader, mobile, category, tl_ok, sr_ok), place creation, leader mobile auto-fill, and submit orchestration. `handleSubmit` accepts both `FormEvent` and `MouseEvent`.
- `app/app/components/useStateDropdowns.ts` — fetches and caches state-scoped place and leader lists. All `setState` calls are routed through Promise chains to satisfy the `react-hooks/set-state-in-effect` rule.

### Public links (`/public/*`)
No-login pages, each registered in `lib/publicLinks.ts` (single source of truth for slug/title/description/path — drives both the page's own `<title>`/Open Graph metadata and the admin-managed list at `/admin/public-links`, where an admin can override a link's title/description without a redeploy). `middleware.ts`'s `PROTECTED_PREFIXES` doesn't include `/public`, so these pages are open by default; each is backed by a matching `/api/public/*` route using `supabaseAdmin` (service role) rather than the browser client, since anonymous visitors have no RLS access. Every `/api/public/*` route calls `enforceOrigin()` and a per-IP `createRateLimiter()` (`lib/corsUtils.ts` / `lib/rateLimit.ts`), and GETs are briefly in-memory cached since the response is identical for every caller.

`/public/training/[campaignId]` (below) is dynamic per-campaign, so it is deliberately **not** in `lib/publicLinks.ts` — that registry is for the fixed, enumerable links listed on `/admin/public-links`, not one entry per campaign. Its title/description are computed from the campaign record in its own `generateMetadata()` instead. Its GET is also not in-memory cached like the others, since each request is a single indexed-row lookup by campaign id rather than a table scan. `/public/campaigns-near-me` (below) is excluded from `lib/publicLinks.ts` for the same reason — personalized per registrant (`?r=<id>`), not a fixed link — and its GET is likewise not cached, since the response differs per registrant.

### Database tables (key ones)
- `campaigns` — core records; `category` column is the campaign category flag (e.g. `TWOL`, `BOTJ`, `TLT`); `place`+`site` together identify the location
- `state_leaders` — leaders per state; `admin` column drives role ('AD' / 'SR' / null); `email`/`pending_email`/`user_id`/`email_confirmed_at` support the leader email-capture rollout (see "Leader email capture" under Auth & roles) — `email` has no DB-level uniqueness constraint (several rows for the same real person, e.g. an AD/SR/leader trio in one state, can share one address), and `user_id` isn't read by any RLS policy yet. `mfa_enrolled_at` (see "MFA enrollment (unenforced)") records when that person completed TOTP/SMS MFA enrollment — also not yet enforced by login/RLS
- `state_leader_email_changes` — append-only audit trail of `state_leaders.email` changes (`source: 'self-serve' | 'admin'`, before/after value) — see `scripts/create_state_leader_email_changes_table.sql`. Excluded from `backupService.ts`'s `BACKUP_TABLE_CONFIG`, same reasoning as `campaign_changes_log`
- `state_places` — valid places per state; keyed on `state`+`place`+`site` (`site` holds a numeric sub-location suffix, e.g. "1" for "Orange 1")
- `campaign_rules` — recurring scheduling rules; also carries `place`+`site`
- `campaign_messages` — per-date banner messages
- `campaign_changes_log` — audit trail
- `results` — recorded result names per campaign; `category_code` is `'TM' | 'P' | 'F' | 'SP' | 'IR'` (Team Member / Partial Presentation / Full Presentation / Full Presentation + Sinner's Prayer / Information Request); `first_name` is free text, not a foreign key to `state_leaders`
- `campaign_interest` — members registering interest via the public `/public/register-interest` link; one row per (campaign, person), with `mobile` and/or `email` (at least one required — DB `CHECK` constraint, see `scripts/create_campaign_interest_table.sql` and `scripts/add_email_to_campaign_interest.sql`). `interest_type` is `'in' | 'more'` ("Yes I'm In" / "Tell Me More"); `contacted` + `contacted_at` track admin/leader follow-up. RLS lets an admin, or the campaign's owning/shared leader, read/update rows, via a join through `campaigns` mirroring that table's own SELECT/UPDATE policy — see `supabase/rls-policies.sql`. The public page inserts via the service role in its API route instead (anonymous visitors have no RLS access). `/api/public/campaigns-near-me` (see the Public links table) also inserts here the same way, for a registry registrant tapping "Yes I'm In"/"Tell Me More" on their personalized map — `first_name`/`mobile`/`email` are re-derived server-side from `registry.registrants`, never taken from the request body. Both insert paths also call `lib/services/campaignInterestSmsService.ts`'s `notifyLeadersOfCampaignInterest()` right after, best-effort texting the campaign's owning leader (see below)
- `campaign_interest_sms_log` — audit trail of every "text the leader" SMS attempt made by `notifyLeadersOfCampaignInterest()` (`scripts/create_campaign_interest_sms_log_table.sql`). One row per leader per submission (`campaign_ids` is an array — several ticked campaigns for the same leader are one combined text, one log row), `status` is `'sent' | 'failed' | 'skipped_no_mobile'`. Admin-only RLS `SELECT`; only the service role writes (bypasses RLS, no INSERT policy needed) — see `supabase/rls-policies.sql`. Excluded from `backupService.ts`'s `BACKUP_TABLE_CONFIG`, same reasoning as `campaign_changes_log` (a log table, not admin-curated content)
- `training_interest` — members registering interest in a training session via its per-campaign public link (`/public/training/[campaignId]`); one row per (campaign, person), with `mobile` and/or `email` (at least one required — DB `CHECK` constraint, see `scripts/create_training_interest_table.sql`). `contacted` + `contacted_at` track follow-up, same as `campaign_interest`, and RLS follows the identical owning/shared-leader-or-admin pattern — see `supabase/rls-policies.sql`
- `campaign_reports` — Campaign Report project (`docs/campaign-report/BRIEF.md`): aggregate per-campaign tallies (Partial/Full Presentations, Sinner's Prayer, Information Requests) from Jordan's Google Sheet, loaded via `scripts/campaign_reports_xlsx_to_json.py` + `scripts/import_campaign_reports.ts` (`lib/campaignReportParser.ts` owns the parsing rules, unit tested). `location_raw`/`leader_raw` are free text — no FK to `state_places`/`state_leaders`; `campaign_id` is a nullable, unenforced best-effort link for a future cleanup pass. Every tally/date column has a paired `*_raw` text column (a leader sometimes typed a note instead of a number/date) and `needs_review` flags rows the parser couldn't confidently parse. `submitted_at` (the sheet's own submission timestamp) is unique — the de-dup key for re-running the import against a newer export.
